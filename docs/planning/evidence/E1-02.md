# E1-02 diagnostic run recipe and evidence boundary

The [diagnostic](../../../tests/diagnostics/e1-baseline.php) runs the unmodified 2.0 backend against a **disposable** database named exactly `wp_lock_e1`. It drops and recreates only `e1_lock` there. Its explicit `WP_LOCK_E1_DISPOSABLE=wp_lock_e1` acknowledgment, socket check, and post-connect database-name check are safety guards, not permission to point it at a consumer server. It uses passwordless `root` over a Unix socket solely for the isolated containers below. It does not load a WordPress test database or its `wp-tests-config.php`.

Run one engine at a time. The checkout's `wordpress-develop/src` supplies `wpdb`; PHP must have `mysqli`, PCNTL, and POSIX. Missing process control exits 2. The shown engine versions match the prior audit; record actual `VERSION()` rather than assuming the image tag. The commands below create a fresh server with networking disabled and database files in container tmpfs. Keep logs outside the socket bind directory: the entrypoint may change that directory's ownership. `mysqladmin ping` alone can see the temporary initialization server before `wp_lock_e1` exists. Run this bounded readiness helper in the same shell; the `&&` commands below invoke PHP only after it returns 0:

```bash
e1_wait_database() {
  for ((attempt = 0; attempt < 90; attempt++)); do
    if docker logs "$1" 2>&1 | grep -Fq 'init process done. Ready for start up.'; then
      if docker exec "$1" "$2" --socket=/e1/mysql.sock --batch --skip-column-names wp_lock_e1 -e 'SELECT DATABASE()' 2>/dev/null | grep -Fxq wp_lock_e1; then
        return 0
      fi
    fi
    sleep 1
  done
  docker logs --tail 80 "$1" >&2
  return 1
}
```

```bash
mkdir -p /tmp/wp-lock-e1/mysql-socket /tmp/wp-lock-e1/logs
chmod 777 /tmp/wp-lock-e1/mysql-socket
docker run --rm -d --name wp-lock-e1-mysql --network none \
  --mount type=bind,src=/tmp/wp-lock-e1/mysql-socket,dst=/e1 --tmpfs /var/lib/mysql \
  -e MYSQL_ALLOW_EMPTY_PASSWORD=yes -e MYSQL_DATABASE=wp_lock_e1 \
  mysql:8.0.46 --socket=/e1/mysql.sock --skip-networking --mysqlx=0
e1_wait_database wp-lock-e1-mysql mysql &&
WP_LOCK_E1_DISPOSABLE=wp_lock_e1 \
WP_LOCK_E1_SOCKET=/tmp/wp-lock-e1/mysql-socket/mysql.sock \
WP_LOCK_E1_WP="$PWD/wordpress-develop/src" \
php7.4 tests/diagnostics/e1-baseline.php > /tmp/wp-lock-e1/logs/mysql.jsonl 2> /tmp/wp-lock-e1/logs/mysql-runner.stderr
mysql_status=$?
docker logs wp-lock-e1-mysql > /tmp/wp-lock-e1/logs/mysql-container.log 2>&1
docker stop wp-lock-e1-mysql
printf 'MySQL readiness/runner exit: %s\n' "$mysql_status"
```

```bash
mkdir -p /tmp/wp-lock-e1/mariadb-socket /tmp/wp-lock-e1/logs
chmod 777 /tmp/wp-lock-e1/mariadb-socket
docker run --rm -d --name wp-lock-e1-mariadb --network none \

  -e MARIADB_ALLOW_EMPTY_ROOT_PASSWORD=yes -e MARIADB_DATABASE=wp_lock_e1 \
  mariadb:10.11.10 --socket=/e1/mysql.sock --skip-networking
e1_wait_database wp-lock-e1-mariadb mariadb &&
WP_LOCK_E1_DISPOSABLE=wp_lock_e1 \
WP_LOCK_E1_SOCKET=/tmp/wp-lock-e1/mariadb-socket/mysql.sock \
WP_LOCK_E1_WP="$PWD/wordpress-develop/src" \
php7.4 tests/diagnostics/e1-baseline.php > /tmp/wp-lock-e1/logs/mariadb.jsonl 2> /tmp/wp-lock-e1/logs/mariadb-runner.stderr
mariadb_status=$?
docker logs wp-lock-e1-mariadb > /tmp/wp-lock-e1/logs/mariadb-container.log 2>&1

printf 'MariaDB readiness/runner exit: %s\n' "$mariadb_status"
```

The runner emits JSON lines: actual PHP/WordPress source path, server version, InnoDB, strict SQL mode, and normalized RR/RC session isolation; each concurrency case also records three distinct connection IDs. Its ordered control confirms a WRITE or READ owner is present before an independent WRITE contender runs, retains ownership through observation, then confirms the contender succeeds after release. The empty-key rounds instead use a shared start barrier; they sample SQL scheduling and do **not** force a specific read/insert interleaving. Each pair holds acquired rows until both results and row count are observed. Children have 15-second socket reads, a five-second reap deadline, and forced termination on failure.

All diagnostic backend instances use the existing constructor default of three database-error retries after the initial query (`WP_Lock_Backend_DB::DEFAULT_DB_ERROR_RETRIES`); the 0.1-second argument sets only the blocking timeout. Pair results count rounds with SQL errors and retain at most two samples per case with round number, both acquisition results, and the returned error messages. A case with any error still fails its expected RED/GREEN check. The samples are diagnostic evidence, not an error waiver.

Expected legacy **RED** observations are at least one dual WRITE or READ/WRITE acquisition under RC, an outer caller rollback permitting a second WRITE while the first backend still believes it acquired, and TTL overlap after expiration. The strict-mode backend should reject 51 ASCII characters, 51 Unicode characters, and two IDs with a common 50-character prefix. Expected **GREEN** controls are no sampled dual conflict under RR, simultaneous READ/READ on both isolations, the ordered owner/contender sequence on both isolations, a 26-character/52-byte Unicode ID accepted by a `varchar(50)` character column, and old-ID release preserving the TTL successor. An RC run without a dual acquisition exits 1 as inconclusive, not as proof of safety; a sampled RR pass is not a proof of all schedules.

The D6 nullable-column checks use **raw SQL feasibility probes**, explicitly separate from production backend behavior. They insert `original_key=NULL` under strict mode using `md5()` of each complete PHP string for `lock_key`, then read both columns back. The common-prefix suffixes must produce distinct keys. This tests whether optional diagnostic omission works without DDL; it does not implement or approve a policy for retaining arbitrary full IDs. No trigger or query filter is injected in this runner. The [saved audit probe](../../review-2026-09-29/probe.php) contains separate fault injection and is not run by this recipe.

Evidence to attach after execution: exact checkout revision/diff, commands and exit codes, the two JSONL files, actual server/PHP/WordPress versions, and any deviations. `pass=true` in the final summary means the legacy observations and controls matched on that sampled run; it does not mean the backend meets the target 3.0 contract. Run `composer test` separately in its isolated WordPress test environment as the existing-suite gate. Commit/review/merge and independent E1-QA remain separate delivery gates.

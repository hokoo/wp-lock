# E3-02 foundation implementation and required runtime evidence

**Final local verification, 2026-10-01:** the frozen B1 foundation passed the six-row disposable MySQL/MariaDB diagnostic matrix at both RR and RC, and the existing PHPUnit suite passed with 54 tests, 143 assertions, and no skips. The [retained manifest and outputs](e3-02/manifest.md) give exact commands, source hashes, runtime versions, per-row exits, and limits. This is B1 feasibility and regression evidence. The delivery owner reviewed the local implementation and runtime evidence; required PR review and batch merge remain pending. Public ownership switching, E3 epic QA, full release matrix, and coverage remain later gates.

The B1 implementation is an **inactive** 3.0 foundation. `WP_Lock_Backend_DB::acquire()` and `release()` still execute the legacy 2.0 protocol; legacy caller-rollback and RC ownership defects remain for E3-03. No 3.0 owner is granted until the later migration barrier. The foundation schema is prepared only by an explicit `WP_Lock_Foundations::prepare_schema()` call, on an independent connection. It adds a permanent `lock_resource` table and a nullable unique `attempt_token` owner column. The schema-only option is written through that independent connection only after InnoDB, required columns, indexes, and routing verify; it is not a protocol switch.

The foundation accepts only an ordinary `wpdb` using `DB_*` settings. It compares the caller and controlled session's database, server host/port/id and distinct connection IDs, checks writable routing and controlled autocommit, then checks session identity around statements. A drop-in/proxy that cannot meet this bounded identity check fails closed. This check cannot certify every possible proxy topology; support for a particular drop-in needs a separate routing test. A captured namespace is used for foundation operations after prefix changes. Legacy public release still uses mutable `$wpdb->prefix` until E3-03.

The directed diagnostic uses the real foundation methods and only the named disposable `wp_lock_e1` database. It requires PCNTL/POSIX and exercises schema installation, invalid schema/failed DDL without marker advancement, strict diagnostic IDs, finite timeouts, two first creators serialized on the unique resource row, RR/RC locking reads, coexisting readers, caller rollback and namespace capture, token uniqueness, committed/rolled-back token reconciliation after injected INSERT/COMMIT acknowledgment loss, and failure when routing or session identity cannot be established. A test-only `wpdb` subclass throws after its real SQL call succeeds, before the foundation sees the result; a separate fault kills the controlled connection immediately before INSERT. The production controlled `wpdb` disables automatic reconnect/replay, so a lost transaction cannot silently issue the INSERT on a fresh session. The test closes the old session before checking the exact token under a resource lock on a fresh primary session. These checks are feasibility evidence only; they do not establish public 3.0 acquire/release safety.

**Earlier failed attempts, retained as diagnostic history:** the first six-row run at `/tmp/wp-lock-d1.SCDJzSxQ` stopped before `install` on MySQL 26.7 because `information_schema` returned uppercase labels while column validation expected lowercase. The repair aliases metadata fields, checks unique and prefix indexes, retains representable utf8/utf8mb3 diagnostics, uses query-boundary fault injection, and disables automatic write replay. That run had no passing matrix row.

The second run at `/tmp/wp-lock-d1.ZTXd4SHM` passed the first MySQL row through RR/RC ownership and fault cases, then failed the routing/reconnect case because its `wpdb` test subclass lacked the expected `e3_` prefix. The fixture copied the normal prefix to reach the routing guard, and its deprecated reflection setup was limited to PHP before 8.1. No complete row passed in that run.

The third run at `/tmp/wp-lock-d1.hScpDP6T` passed both MySQL rows, then failed before MariaDB 13.0 `install` because its `read_only=OFF` enum was not recognized as writable. The routing guard now accepts exact `0` or `OFF` and rejects restrictive or unknown values. [MariaDB documents its newer `read_only` enum](https://mariadb.com/docs/server/server-management/variables-and-modes/server-system-variables#read_only). This was a partial matrix.

The fourth run at `/tmp/wp-lock-d1.40cfk0Hl` passed both MySQL rows and the initial MariaDB 13.0 cases, then failed at `current_read_REPEATABLE READ` with a generic SQL error. The diagnostic gained phase, numeric MySQL error, SQLSTATE, and redacted DB-error reporting while preserving the current-owner assertion.

The fifth run at `/tmp/wp-lock-d1.1qBqC2M2` identified MariaDB 13.0.2 RR `current_read / resource_lock` errno 1020, SQLSTATE HY000 (`record changed since snapshot`). The [accepted D2 clarification](../adr/001-contract.md#d2-clarification--controlled-mariadb-snapshot-isolation-2026-10-01) permits `innodb_snapshot_isolation=OFF` only on the independent WP Lock connection. The foundation now verifies that controlled setting when exposed and refuses a failed setup. The diagnostic verifies unchanged caller state, including during an outer transaction, and a rejected controlled setting. The final retained run verifies this repair on all six rows.

The first existing-suite attempt at `/tmp/wp-lock-b1-suite.fjqIND42` exited 255 before tests: Composer loaded the foundation class before WordPress defined `wpdb`. The no-reconnect subclass was moved to `class-wp-lock-foundation-db.php` and loaded when the independent connection opens. Composer-files and deferred-subclass smoke checks, `php -l`, and `git diff --check` passed after that repair. The successful suite run is retained below. The failed suite's disposable database container was removed. Setup regenerated ignored `vendor/composer/autoload_classmap.php`, `autoload_files.php`, and `autoload_static.php`; these were left untouched and have no tracked-source effect.

A later suite attempt at `/tmp/wp-lock-b1-suite-retry.34xfUJnQ` exited 1 before tests when sandboxed PHP received `Operation not permitted` connecting to its disposable database Unix socket; the approval attempt timed out. The final suite run used the same bounded disposable setup after that environment failure.

These sampled schedules and simulated post-query acknowledgment losses establish feasibility of the inactive foundation, not public acquisition safety or physical packet-loss behavior.

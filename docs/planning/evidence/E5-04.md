## Isolated package smoke

Once the root commits the implementation, run this **once** on that exact checkout, substituting its full 40-character SHA:

```bash
E5_DOCKER='/mnt/c/Program Files/Docker/Docker/resources/bin/docker' E5_COMPOSER=/usr/bin/composer bash tests/diagnostics/e5-package-smoke.sh <frozen-implementation-sha>
```

The script retains `/tmp/wp-lock-e5-package.XXXXXXXX` with the archive and SHA-256/file list, copied install tree hashes, Composer lock/install logs, image/source hashes, actual runtime/engine/isolation, RR/RC JSONL, child process and connection identities, and cleanup exit. It requires a separate `wp_lock_e5_package` MySQL 9.7.2 database on a network-disabled, tmpfs-backed container, PHP 8.5.11 and released WordPress 7.1.2. The package is installed by Composer into a separate consumer directory as a copied dependency, then loaded only through that consumer's `vendor/autoload.php`; the smoke rejects a source-only/autoload-only substitute. An empty namespace is prepared and explicitly switched before acquisition. Two independent READ children retain their grants while a WRITE is refused; a WRITE child retains its grant while READ and WRITE are refused. The parent checks exact remaining owner IDs after each release, then zero owners at both RR and RC. All process, database-readiness, Docker, and cleanup waits are bounded.

This smoke uses a focused `wpdb` bootstrap from released WordPress core. It does not exercise a full WordPress admin request, plugin activation, production admissions barrier, external writes, or a published registry install. The [E5-01 runbook](../../migration.md) and earlier full native suite cover distinct requirements; a successful local smoke cannot replace exact-head remote candidate CI, B5 merge, or independent E5-QA. Any implementation change after freeze requires a new SHA and targeted re-verification before acceptance.

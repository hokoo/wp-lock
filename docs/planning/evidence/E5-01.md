The migration procedure follows accepted [ADR 001 D5](../adr/001-contract.md#d5-installation-switch-and-rollback). The 2.0 owner-table marker remains `2.0.0`; the additive foundation marker is `3.0.0-foundations`; a separate protocol option enables bundled 3.0 acquisition. New acquisitions read that option from the controlled primary connection after complete schema validation. Switches verify schema, route, foundation marker, and zero owner rows, then write and read back the protocol option. The zero-owner observation and option write use controlled autocommit statements, **not** one database transaction; safety across that interval depends on the externally held admissions barrier. Release and manual reconciliation remain callable when new 3.0 admission is disabled. Any uncertain switch result requires fresh primary reconciliation under the barrier.

The directed rehearsal is `D1_DIAGNOSTIC_SCRIPT=tests/diagnostics/e5-migration.php D1_REQUIRE_PASS=1 bash tests/diagnostics/d1-matrix.sh`. It uses the existing six disposable database/PHP/WordPress rows at RR and RC and exports the actual `v2.0.0` library tag into a read-only mount for an independent legacy PHP participant. The JSONL records environment, independent process identity, schema tables/columns/indexes, the three marker values, and owner rows before and after failed DDL, preparation, malformed token default, TTL=0 refusal, interrupted option write, enabled 3.0, and rollback. The fixture barrier positively prevents a new old worker from starting after the held old worker has been stopped and reaped. It does not prove a real site's HTTP, queue, cron, or worker controls.

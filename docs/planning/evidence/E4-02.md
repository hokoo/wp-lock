# E4-02 finite deadline implementation boundary

**State:** implementation and directed six-row verification accepted by root; full suite and coverage, independent E4 QA, and B3 review/merge remain pending. E4-02 is `review`, not completed.

The bundled backend uses one monotonic elapsed budget for positive blocking waits, contention polling, and database-error retries. The controlled connection checks it before each SQL query, including nested setup, route verification, and resource-row upsert/read queries. The caller-side diagnostic-key lookup is followed by a check before owner insertion. A successful `START TRANSACTION` is tracked before its subsequent route check so an expired budget can still roll back; rollback and connection closure are allowed after expiry. Database-error paths roll back and check the same budget before retrying. An expired retry with no proven conflict remains an error rather than becoming contention `false`. Zero-budget blocking and nonblocking calls retain one database acquisition attempt and do not poll.

The owner INSERT is checked at its SQL boundary; once it starts, transaction completion and exact-owner reconciliation take priority over the elapsed wait budget. A committed attempt that finishes after a positive wait deadline is reconciled by its captured namespace, attempt token, and exact owner ID before `false` is returned. Failed or unknown cleanup keeps the unresolved token and raises `WP_Lock_Ownership_Uncertain`. A commit whose result cannot be confirmed likewise keeps an unresolved attempt for `release()` reconciliation. Database-time TTL remains distinct from the monotonic wait deadline. Synchronous database I/O may outlast the wait budget; no hard wall-clock return-time guarantee is made.

Directed cases added to `tests/diagnostics/e4-timing-cases.php` cover delayed database-time read, resource upsert and diagnostic lookup boundaries; exhausted SQL errors; zero and nonblocking first attempts; alternating SQL errors and contention; late commit with confirmed or failed cleanup; and uncertain commit. Corresponding PHPUnit cases cover slow `START TRANSACTION`, resource upsert, failed rollback, diagnostic lookup, and the earlier E4-02 cases. The existing E3/E4 controls remain in the same diagnostic route.

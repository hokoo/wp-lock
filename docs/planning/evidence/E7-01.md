# E7-01 analyzer baseline and local verification

**Boundary:** `batch/b6`, working tree before commit or merge, 2026-10-05. This is task evidence, not the final 3.0.0 candidate or an E7 QA verdict.

## Selection and initial findings

The checked scope is every `lib/**/*.php` file (seven files) and `plugin.php` (one file). `WordPress-Core` checks the WordPress coding rules relevant to this library. The broader `WordPress` set also adds documentation and extra best-practice policies outside this focused style gate. The initial command `php7.4 vendor/bin/phpcs --standard=WordPress-Core --report=json lib plugin.php` reported **127 errors and 61 warnings across eight files**. The largest categories were alignment (55), function-call layout (73), and indentation (20). The remainder included short arrays (6), SQL interpolation (7), established filenames and multiple classes (7), reserved `$namespace` parameter names (4), direct driver error codes (2), legacy loose option comparison (2), and one short ternary. Warnings remain enabled and fail the command.

Before adding WordPress definitions, `php7.4 vendor/bin/phpstan analyse lib plugin.php --level 0 --no-progress --debug --error-format=json` reported seven missing WordPress symbol errors: `wpdb` and its parent methods/property, `apply_filters`, `wp_parse_args`, and `dbDelta`. The analysis-only `phpstan-wordpress.php` contains only WordPress symbols used by this package, with method names checked against the local WordPress core signatures; its untyped return declarations give PHPStan limited type information. It is scanned, never autoloaded by Composer or used at runtime. `ABSPATH` is dynamic because an installed WordPress path is not part of a clean analyzer checkout.

With the WordPress declarations present, measured PHPStan findings by level were: 0 → 0; 1 → 11; 2 → 11; 3 → 16; 4 → 24; 5 → 24; 6 → 68. Level **3** is the lowest level in this measurement that exposed the incorrect lock-owner array annotation as well as the possible undefined `$namespace` catch-path variable. The correction records the actual array shape and initializes `$namespace` before the acquisition loop. Every catch use is guarded by a non-null token, which is created only after `$namespace` receives its real value, so the initializer is not observable at runtime. Level 4 adds inferred always-true guards involving deliberately validated public arguments, retry flow and connection state; resolving those would require changing established runtime defenses or individually analyzing legacy branches beyond E7-01.

## Narrow style exceptions

`phpcs.xml.dist` keeps `WordPress-Core` and excludes only established autoload filenames (`class-wp-lock-backend-db.php`, `class-wp-lock-foundations.php`, `Database.php`), the two files that intentionally declare exception classes alongside their main class, and the four `$namespace` parameter names in `class-wp-lock-foundations.php` whose renaming could affect PHP 8 named calls. No whole-file analyzer exclusion or PHPStan baseline is used.

Inline PHPCS comments at four SQL statements explain seven existing interpolation finding messages involving dynamic SQL identifiers and an already prepared optional filter. Other comments explain two direct `mysqli` error-code reads on the controlled connection, two legacy option comparisons, and one `getmypid() ?: 0` expression. The SQL text, table/namespace resolution, bind values, driver diagnostic path, option coercion, and PID fallback were preserved. PHPCBF fixed the remaining 165 layout and syntax-style findings; final PHPCS output has **zero errors and zero warnings**.

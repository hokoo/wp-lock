## Evidence and constraints

The [audit](../../review-2026-09-29/assessment.md) ran the unmodified 2.0 backend with independent PHP processes and connections, InnoDB, WordPress 6.2, PHP 7.4.3, MySQL 8.0.46, and MariaDB 10.11.10. It observed simultaneous conflicting owners under READ COMMITTED, but none in its sampled REPEATABLE READ runs. It also reproduced caller `ROLLBACK` removing a lock, acquisition returning an already expired lease after slow SQL, a database error appearing as absence, and strict-mode rejection of a 51-character resource ID. These are observations about 2.0, not proof of a replacement. The separate existing-suite run used PHP 8.3.33, WordPress 7.1-src, and MariaDB 10.11.10; 51 tests / 140 assertions passed despite the audit findings. The [current CI](../../../.github/workflows/phpunit.yml) exercises PHP 7.4–8.3 with WordPress 7.1 and MariaDB only. No target-protocol, full matrix, drop-in, or migration run has occurred.

The [public interface](../../../lib/backend/class-wp-lock-backend.php) returns booleans; the [wrapper](../../../lib/class-wp-lock.php) marks itself held only after successful acquire and retains held state after failed release. The [DB backend](../../../lib/backend/class-wp-lock-backend-db.php) derives `md5($id)` from the complete string, stores an auto-increment `id` for release, and currently derives its physical table from mutable `$wpdb->prefix`. These mechanisms should survive where they are safe. The [roadmap](../../../ROADMAP.md#v300) requires successful shared READ/exclusive WRITE acquisition on both RR and RC and forbids concurrent incompatible protocols.

## D2 protocol and identity

For a lock operation, capture the WordPress table prefix/physical namespace at acquisition and keep it with the held owner. A blog/prefix switch cannot redirect that owner's release or recovery; a new unheld lock uses its then-current namespace. Within that namespace, retain `md5()` of the **entire** resource ID as the 2.0 lock key. A resource row has this key as a unique/primary key and is not deleted during ordinary release or cleanup. Its one-time creation must be atomic under a unique constraint: concurrent creators either create it or wait for the winner, then lock the committed row. Do not rely on a `SELECT` of a missing row or a non-unique owner-table gap. Collision risk of the existing MD5 identity is unchanged; a change to resource-key derivation would need a separate migration decision.

Every acquire uses a fresh, controlled transaction on a DB connection independent of global `$wpdb`, routed to the same writable primary/schema as the owner table. Create/find the resource row, lock it by its unique key, then read conflicting owner rows with a **current locking read**, expire eligible finite owners, insert a READ or WRITE owner only if compatible, and commit before returning success. READ/READ may insert separate owner rows; READ blocks WRITE and WRITE blocks both. Acquiring the resource row first for release and cleanup gives every mutator the same order. Under RR, a plain consistent `SELECT` may use an older read view; the owner read cannot use it. MySQL documents the difference between [consistent and locking reads](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html), and MariaDB documents that [`FOR UPDATE` needs a transaction](https://mariadb.com/docs/server/reference/sql-statements/data-manipulation/selecting-data/for-update). Unique-row creation/locking and all ordering still require controlled interleaving tests on both engines.

Use the existing owner `id` from `insert_id` for normal release and local bookkeeping. Generate and store a unique random attempt token **before every new owner INSERT**; its sole added purpose is recovery because transport loss before the INSERT response can erase `insert_id`, and transport loss during COMMIT can leave durability unknown. An attempt must never be blindly repeated: on a fresh primary connection, reconcile its token under the resource-row lock after the prior transaction is resolved. If the old connection/transaction cannot be proven ended, return uncertainty and preserve the possibility of ownership. A confirmed row belongs to that attempt; a confirmed absence after resolution permits a new attempt. Token lookup must not identify another owner's row, and token presence alone does not prove an unexpired lease. This is a feasibility gate, not a claim that the required fault handling is already implemented. If token lookup cannot be made reliable on a supported connection path, D2 needs revision before implementation.

An `acquire()` that throws after an uncertain INSERT/COMMIT does **not** grant the caller permission to enter its protected work. The bundled backend retains the attempt token and captured namespace; the wrapper retains a separate unresolved state even though its confirmed-held bit is false. On a later call using the same wrapper/backend, reconcile that attempt before any new acquisition: prove the old transaction has ended, then use a fresh primary connection and the resource-row lock to check the exact token. A confirmed absent row clears the unresolved state. A confirmed present row is released by its exact owner identity, including a TTL=0 row, because this call never returned a grant; only a confirmed release clears the state. A failed or uncertain lookup/deletion remains unresolved and requires the maintenance-barrier/manual-recovery path if retry cannot settle it. `release()` on this unresolved wrapper may drive that reconciliation and return only after confirmed cleanup; `lock_exists()` remains an observation and never clears uncertainty or authorizes work. These are internal lifecycle semantics using the existing `acquire`/`release`/`exists` surface under accepted D2 and D6. No new public method or retroactive successful acquire is proposed. A new wrapper cannot repair the old wrapper's lost token, so callers must retain/report an unresolved instance and must not use a fresh instance to assume the old attempt was absent.

The controlled connection must not inherit or alter the caller's active transaction, autocommit, or isolation. Validate independent session identity, same primary database, InnoDB tables, and expected isolation/transaction state; fail closed if routing or reconnection cannot be established. A deadlock rolls back the **entire controlled transaction**; retry the complete attempt only after outcome is known and within the wait budget. A lock-wait timeout may roll back only a statement, so explicitly roll back the controlled transaction before retrying. Neither case may commit/roll back caller work. MySQL documents these different [InnoDB error outcomes](https://dev.mysql.com/doc/refman/8.0/en/innodb-error-handling.html). If the connection changes or COMMIT acknowledgment is lost, report an unknown outcome until token-based reconciliation proves it. Do not treat an empty `$wpdb->last_error`, a reconnect, or a failed probe as commit confirmation.

The accepted D2 architecture uses one added resource table and one nullable unique attempt-token column in the existing owner table. It does **not** require a new owner table, a fencing generation, renewal state, or a generic adapter. An independent connection is the minimum separation from caller transactions; compatibility with WordPress DB drop-ins/proxies needs a declared support boundary and real test. If that connection cannot be verified on a target installation, refuse the bundled backend rather than fall back to global `$wpdb` for ownership mutations.

Alternatives considered:

| Alternative | Disposition |
| --- | --- |
| Keep the existing `INSERT … SELECT NOT EXISTS` | Reject for 3.0: the audit reproduced conflicting owners under RC; sampled RR success is not a proof. |
| Add `UNIQUE(lock_key)` to owner rows | Reject: it disallows legitimate shared READ owners. |
| Lock the absent owner-table range or add `FOR UPDATE` around the old check | Reject as the sole protocol: absence has no common durable row under RC, and RR snapshots still need explicit current reads. |
| MySQL/MariaDB `GET_LOCK()` as resource mutex | Defer: it is exclusive and session scoped; shared READ, TTL and uncertain reconnect would still need an owner-row protocol. It would exchange one small table for more connection/proxy dependence. [MySQL locking functions](https://dev.mysql.com/doc/refman/8.0/en/locking-functions.html) document session ownership. |
| Global DB mutex or table lock | Reject as the release protocol: it serializes unrelated resources and creates unnecessary contention. |

### D2 clarification — controlled MariaDB snapshot isolation (2026-10-01)

OWNER accepted setting and verifying `innodb_snapshot_isolation=OFF` **only on the independent WP Lock connection** when the server exposes that variable. Preserve the configured RR/RC isolation and leave the caller connection unchanged. Refuse the foundation if the controlled-session setting cannot be established and verified. This responds to the B1 MariaDB 13.0.2 RR feasibility failure (errno 1020 / SQLSTATE HY000, record changed since snapshot) retained at `/tmp/wp-lock-d1.1qBqC2M2`; MySQL 26.7 and 9.7 passed that attempt. ## Time, results, and recovery contract

The database primary is the authority for finite owner expiry; PHP host wall clocks do not decide it. Take database time **after** obtaining the resource lock, issue the finite expiry then, and make a fresh database-time check after COMMIT and before reporting success. `NOW()` is evaluated at statement start, so a timestamp from a statement that waited must not become the lease start; see [MySQL date/time functions](https://dev.mysql.com/doc/refman/8.0/en/date-and-time-functions.html). A known-expired or zero-remaining lease cannot be reported as a grant. Even a valid return cannot prevent expiry during a later PHP pause or fence arbitrary external writes. The wrapper's held bit records its last confirmed lifecycle result, not permanent ownership. A later observed loss must be explicit. Renewal and application fencing remain outside 3.0.

Measure blocking wait and error-retry budget with a PHP monotonic clock. A zero timeout or nonblocking call permits **one database acquisition attempt** and no contention polling; the clock must not reject that first attempt merely because its deadline equals its start. A finite positive blocking timeout is a wait budget checked before each retry and after every SQL result, including error paths. A synchronous SQL call may outlast that budget; this is not a hard return-time SLA. Owner expiry is a separate database-time TTL measured after the resource lock is obtained, never the PHP wait deadline. If a late attempt definitely acquired, release its exact owner under the protocol and return `false` only after successful cleanup; a failed or unknown cleanup raises uncertainty and preserves owner identity. Never turn a confirmed owner into a contention `false`. Preserve the configured finite zero/positive timeout behavior; reject non-finite inputs before time arithmetic.

Accepted D6 result distinction for the public wrapper and bundled backend, pending implementation and verification:

| Observation | Public result / local state |
| --- | --- |
| Compatible committed owner, valid remaining TTL | `acquire() === true`; record `insert_id` and attempt token; wrapper held. |
| Proven conflict or expired waiting budget, with no committed owner from this attempt | `acquire() === false`; wrapper unheld. |
| DB/connection error with known rollback and no owner, or failed `exists()` query | Throw `RuntimeException` (or a named subclass); do not return contention/absence. A successful `lock_exists()` query returns its existing boolean meaning and never authorizes entry. |
| Commit, reconnect, release, or cleanup outcome unresolved | Throw a distinct `RuntimeException` subclass for **ownership uncertain**, retaining any recoverable handle and blocking a blind new attempt until reconciliation or manual recovery. If acquire had no confirmed handle, keep the attempt token and unresolved wrapper state; a later `release()` may reconcile it but cannot silently discard it. |
| Ownership definitely expired, removed, or replaced | Throw a distinct **ownership lost** `RuntimeException` subclass when the caller acts on that handle; clear that confirmed-lost wrapper handle so it cannot masquerade as held. A failed/uncertain release, by contrast, remains retryable and held. |

This exception distinction is an accepted D6 public contract design, subject to implementation and verification. The existing backend interface can retain `bool` signatures; custom backends are not required to produce new exceptions, but wrapper handling and documentation must remain compatible with their existing true/false behavior. Do not silently reinterpret custom-backend `false` as proven loss.

Release is idempotent only for the exact recorded owner `id` **and** token within the captured namespace. Confirmed deletion clears the handle; failed DELETE/COMMIT keeps it for reconciliation or retry, and a confirmed missing old row reports loss without deleting a successor. Expired finite owners may be removed only while holding the resource row, by their exact identity; a predecessor's later release cannot remove a new owner. A failed SELECT, processlist query, DELETE, or commit is uncertainty, never proof that the resource is empty. TTL=0 records are never automatically selected using PID/CID liveness; those columns may remain diagnostics only.

**Consumer TTL warning (D3):** TTL=0 has no automatic expiry; a fatal request, process crash, or network failure can leave an owner that requires manual recovery after stopping all participants. Prefer a nonzero TTL longer than the **maximum expected bounded duration of the protected critical section**, with generous margin for SQL, network, and scheduling delays; PHP-FPM worker lifetime is not the sizing basis. Always release explicitly, including in `finally` where applicable. Expiry may let a successor acquire while the original PHP work still runs, so no finite TTL guarantees safety for unbounded or stalled operations. An arbitrarily large TTL lengthens recovery after a crash; confirmed explicit release ends normal ownership immediately.

Accepted manual TTL=0 recovery design, to be implemented and rehearsed on isolated databases before publication:

1. Stop **all** acquisitions for the captured namespace, quiesce old/new workers, and confirm no participant can still enter or write under the old lock. Keep the maintenance barrier in place throughout recovery.
2. Identify the exact physical table/resource key and owner `id`/token, inspect the owner row on the primary, and confirm the owning operation has ended using application/process evidence outside PID/CID alone. A failed query, incomplete process visibility, or unknown operation state blocks deletion.
3. Under the same resource-row serialization protocol, delete only the verified stale owner identity; verify the deletion and remaining owners by fresh primary reads. For a legacy row lacking a token, use its `id` only while old participants are fully stopped and recheck it before deletion.
4. Record namespace, resource, owner, reason, operator, time, SQL outcome, and postcondition; resume acquisitions only after every unresolved owner is reconciled. If a query/commit is uncertain, leave the barrier in place and escalate rather than assume release.

At ADR acceptance this procedure was unverified; isolated rehearsals are now recorded in [E4 QA](../qa/E4.md) and [E5-01 evidence](../evidence/E5-01.md). Design acceptance is not authorization to delete production records. Finite expired rows follow the database-time rule, not PID/CID tests.

## D5 installation, switch, and rollback

Schema preparation may add the resource table and nullable token column while 2.0 still runs only if rehearsed DDL is compatible with old inserts. Verify engine, keys, columns, indexes, namespace table, and connection routing completely before writing a 3.0 schema/protocol version; a partial `dbDelta` or DDL failure leaves 3.0 acquisition disabled. No new owner may be granted by 3.0 until the following barrier completes:

1. Disable admissions and stop **every** 2.0 worker/queue/cron participant for the affected site/blog namespace; verify they cannot restart on 2.0 code. No rolling overlap is supported.
2. Wait for finite owners to release or expire and resolve every TTL=0 or uncertain owner using the verified manual procedure. Query the primary and record owner-row counts/identities. A fixed sleep is insufficient.
3. Validate complete 3.0 schema and controlled primary connection on every namespace to be enabled; atomically record the protocol switch only after the barrier is held. Restart only 3.0 participants, then prove a READ/READ and exclusive WRITE smoke path.

On failure **before** enabling 3.0, keep 2.0 stopped until schema and owner state are understood; do not mark the target version. On failure **after** enabling it, stop all 3.0 participants, reconcile every owner (including TTL=0 and uncertain outcomes), verify no 3.0 work remains, then restore the compatible 2.0 schema/version and restart old participants only in its documented safe environment. The 2.0 RC race remains a rollback risk and must be explicit; rollback is not a way to claim 3.0 guarantees. Rehearse clean install, 2.0 upgrade, failed DDL, interrupted switch, and reverse switch in disposable databases. A DB marker cannot stop an already running 2.0 process that does not read it, so worker quiescence must be operationally enforced and evidenced.

# 2.0 ↔ 3.0 database protocol switch

This is the E5-01 operator procedure. It requires a maintenance window for each physical WordPress database and site/blog table prefix. Rolling coexistence is unsafe: 2.0 ignores the 3.0 protocol option and can still acquire independently. The option only disables **new bundled 3.0 acquisitions**. A site operator must enforce the admissions barrier outside this library across requests, cron, queues, workers, and every process with old code. Keep that barrier until the intended version is running everywhere. An unknown participant or operation blocks the switch.

Record the repository/package revision, WordPress and PHP versions, primary database identity, exact prefix, engine, isolation, operator, UTC time, participant inventory, and how each admission path was stopped and prevented from restarting. Take a restorable backup. Run every inspection against the writable primary for the captured prefix; do not infer owner absence from a replica or a cached WordPress option.

## Upgrade or clean installation

1. Block every lock admission path and positively stop and join all 2.0 participants. For a clean installation, establish that no old participant exists. Keep an external control that prevents restart. Confirm old operations have finished; a PID or a fixed wait alone is insufficient.
2. On the primary, establish whether the exact `<prefix>lock` table exists (for example, by matching `TABLE_SCHEMA=DATABASE()` and `TABLE_NAME='<prefix>lock'` in `information_schema.TABLES`). If it exists, inspect its columns, record `id`, `lock_key`, `level`, and `expire` for **every** row, include `attempt_token` only if that column exists, and record `SELECT COUNT(*)` from the table. Wait for finite owners to release or expire and be reconciled. An `expire=0` row never drains by time. Resolve each TTL=0 or uncertain owner using [manual recovery](recovery.md) under the same barrier, with exact identity and fresh primary postcondition. If the table is absent on a clean installation, record its absence and positively establish that no 2.0 participant exists; check for zero owner rows on the primary after step 3 creates the table and before step 4. Any failed read, uncertain commit, unexplained row, or unknown participant blocks the switch.
3. On a WordPress CLI process using the **3.0 package** and the affected site's table prefix, call `\iTRON\WP_Lock\WP_Lock_Foundations::prepare_schema()`. This uses an independent primary connection and writes `wp_lock_db_foundation_schema_version=3.0.0-foundations` only after complete InnoDB, column, index, route, and connection verification. Record the pre/post table definitions and options. A DDL error or incomplete schema is a stop; do not enable 3.0.
4. With the barrier still held and the owner count freshly zero, call `\iTRON\WP_Lock\WP_Lock_Foundations::switch_protocol('3.0.0')` from that CLI process. It rechecks the complete schema, foundation marker, independent primary route, and zero owner rows; it writes and reads back `wp_lock_db_protocol_version=3.0.0`. The operation cannot prove that old processes are stopped. If the write or its acknowledgment is uncertain, keep the barrier and read the actual option and owners on a fresh primary connection before any retry or restart.
5. Deploy/restart **only 3.0** participants. While admissions remain controlled, prove two independent READ owners coexist, a WRITE is excluded by either READ, and a WRITE excludes READ and WRITE. Record actual primary/connection/isolation and final owner count. Lift the external admissions barrier only after every participant runs the intended code and smoke checks pass.

The package's old automatic `wp_lock_db_schema_version=2.0.0` option is a legacy owner-table installation marker, not an activation switch. The foundation marker is schema-only. New 3.0 grants require the separate protocol option on the controlled primary; release and recovery remain available while new grants are disabled.

## Interrupted switch and rollback

Before the 3.0 protocol option is confirmed, retain the barrier, inspect the actual primary schema/options and all owners, then repair or restore the additive schema. Never infer a successful switch from a timed-out or failed option write. If 3.0 has been enabled or may have granted an owner, stop and join **all** 3.0 participants and prevent restart; reconcile every finite, TTL=0, and uncertain owner under the barrier. A nonzero or unreadable owner count blocks rollback.

For rollback, run `\iTRON\WP_Lock\WP_Lock_Foundations::switch_protocol('2.0.0')` under the same external barrier. Verify the option on a fresh primary connection and confirm no 3.0 participant or owner remains. The added `lock_resource` table and nullable `attempt_token` column can remain; 2.0 inserts do not require their removal. Restore the previously recorded compatible 2.0 package/schema and restart **only** old participants in an environment where its known behavior is acceptable. Legacy 2.0 can grant conflicting owners under READ COMMITTED; rollback does not retain the 3.0 safety guarantee. If that risk is unacceptable, keep admissions stopped and repair forward.

This procedure must be rehearsed on disposable databases before production use. The E5-01 rehearsal records exact source revision and old-package artifact, commands, before/after schema and marker values, primary/engine/isolation, independent old-process termination evidence, failed DDL and interrupted-option outcomes, TTL=0 refusal and exact recovery, both switch directions, and final smoke results. A fixture admissions barrier demonstrates the test; it does not establish that a real site's requests, queues, and workers can all be stopped.
